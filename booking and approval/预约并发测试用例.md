# 预约与自动任务测试说明

更新于 2026-11-15，对应 develop 的 c8142d7 功能版本。本文按现有测试类列出可复核的覆盖范围，替代早期按候补、辅导员占用等规划编写的测试清单。测试结果与实际验收分开记录，不能把设计用例当作已通过证据。

## 如何运行

必须使用独立测试库。测试会写入用户、资源、预约、审计、任务和照片数据，不能指向实际使用的开发或生产数据库。先在当前PowerShell设置自己的测试库参数：

```powershell
$env:CATALOG_DB_TEST='true'
$env:DB_URL='jdbc:postgresql://127.0.0.1:15439/booking_test'
$env:DB_USERNAME='<独立测试库用户名>'
$env:DB_PASSWORD='<独立测试库密码>'
cd backend
.\mvnw.cmd test
```

连接地址、端口和账号仅为配置格式，需替换为自己已经建立的测试库。没有设置 `CATALOG_DB_TEST=true` 时，需要真实数据库的测试会跳过；构建成功不等于完整数据库测试通过。Flyway自动执行V1至V16，已有迁移不能改写，新增迁移从V17开始。

在另一个终端中，从仓库根目录分别运行：

```powershell
cd frontend
npm ci
npm test
npm run build
```

```powershell
cd worker
npm test
```

CI已配置PostgreSQL17的后端测试、前端测试与构建、worker测试。远程执行结果以GitHub Actions对应提交为准，不用本地结果替代远程状态。

## 编写并发测试

真正的跨线程竞争用例须让测试数据先提交，使每个线程能读取；不能让所有准备数据停留在测试线程未提交的事务中。使用ready与start两道同步屏障同时放行，等待所有线程完成，并同时断言返回结果、数据库记录和审计次数。不能用顺序for循环代替并发。

单线程规则测试可使用 `@Transactional` 在结束时回滚；这与跨线程竞争测试是两种不同场景。当前任务数据库测试中的有效租约互斥与失效恢复采用顺序调用验证，不把它描述成已经做过多worker同时领取压测。

按本用例创建的ID清理关联记录；不要在共享库里运行TRUNCATE或清除其他同学数据。新增关联表时同步维护清理顺序。测试时间使用相对当前时间，并在需要时对齐整点；同一竞争用例共用相同的时段。

## 双账号人工验收

1. 创建一个普通用户和另一个审核员，确认双方不能互相读取个人私有反馈、未归还提醒或受保护照片。审核员不能批准自己的申请。
2. 普通用户预约普通物品应直接确认；预约贵重物品或地点进入待审，由另一位审核员决定。重复点击不重复生成预约。
3. 在独立测试数据中准备开始时间临近的待审申请，保持worker运行；到开始时间后等待扫描，检查本人列表和管理日志中的已过期状态、系统结论与处理时间。
4. 在使用时段内领取物品，再验证到期未归还提醒。确认用户只看本人、管理员可看全部，实物库存仍被占用。
5. 提交归还材料后提醒暂不展示，管理员驳回后再次展示，补拍重提并接受核验后提醒不再展示，实物此时才恢复可借。
6. 暂停worker，确认不会新生成任务结果；恢复后补处理积压。仅在独立测试环境模拟网络失败，检查租约重领、旧令牌拒绝和不重复写记录。

## 验证边界

已在同机的独立Node进程、Java HTTP API与独立PostgreSQL间验证过真实调用、自动过期、提醒去重、未授权拒绝与库存保持占用。浏览器也用隔离接口数据检查桌面和窄屏布局；两类验证不能互相替代。

尚需实际验收的包括两台物理机器部署、多worker同时运行、服务重启与网络故障的长时间场景、真实手机拍照、HTTPS、照片和数据库备份恢复。候补转正、辅导员占用已确认预约、地点结束自动交接等未实现流程不纳入当前通过范围。
