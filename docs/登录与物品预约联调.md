# 用户登录与物品预约联调

## 已可运行的链路

系统管理员建立普通用户账号 → 用户在用户端登录 → 浏览已上架物品 → 选择时段、数量与用途 → 提交预约 → 在“我的预约”查看结果。

- 普通物品：有可借实物且该时段未被占满时返回 `CONFIRMED`。
- 贵重物品：返回 `PENDING_APPROVAL`；审批接口尚未接入，不能把“待审核”显示成预约成功。
- 图片对公开上架物品可直接展示。照片数量不等于实物库存；预约前须在后台录入至少一件编号实物。
- 无公开注册。系统管理员可在管理端“用户账号”创建普通账号，底层调用 `POST /api/v1/users`；用户不需要管理角色。

## 接口契约

登录沿用 `GET /api/v1/auth/csrf`、`POST /api/v1/auth/login`、`GET /api/v1/auth/me`，浏览器保留同源会话 Cookie。写请求携带 CSRF 请求头。

`POST /api/v1/reservations` 需要 `Idempotency-Key` 请求头：

```json
{
  "resourceType": "ITEM",
  "resourceId": 1,
  "startAt": "2026-11-03T09:00:00+08:00",
  "endAt": "2026-11-03T12:00:00+08:00",
  "purpose": "学院活动摄影",
  "quantity": 1
}
```

返回 `201`，字段包括 `id`、`status`、`submissionSeq`、时段和物品名称。相同用户使用相同键及内容重试，返回同一预约；同键不同内容返回 `409 IDEMPOTENCY_CONFLICT`。库存或时段冲突返回 `409 RESOURCE_CONFLICT`。时间必须带时区，采用左闭右开时段 `[startAt,endAt)`。

`GET /api/v1/me/reservations?page=0&size=20` 只返回当前用户的分页预约记录。

V6 迁移创建 `reservations` 表；同一物品的创建事务先锁物品记录，再检查重叠时段已确认数量。序号按获得资源锁后的服务端处理顺序生成。贵重物品待审申请不占用库存，审核通过时必须重新检查容量。

## 对后续模块的交接

- **侯梦豪**：用户端表单和“我的预约”已接真实接口；继续完善手机交互、登录异常、预约取消及第 3 周取还件页面，保留现有请求字段。
- **谢跃明**：继续在预约模块增加审批、会议室和取消状态；不要重写已执行的 V6，后续表结构用 V7 及更高迁移版本。审核通过时必须在事务内再次锁资源并检查时段容量。
- **肖志**：取件、拍照归还和核验可依赖预约 ID 与当前状态；需同谢跃明确认交接状态与实物编号绑定后再新增迁移。

当前尚未完成：审核决定、会议室预约、取件、拍照归还、归还核验适配器、到期任务服务。用户端不得为这些入口显示模拟成功。

## 本地检查

启动数据库、后端和前端后，先在管理端上架一件非贵重物品，配置预约规则并录入至少一个实物编号。再到“用户账号”建立普通账号，以该账号登录用户端提交预约。可通过 `GET /api/v1/me/reservations` 或页面“我的预约”核对结果。

后端完整测试在独立临时 PostgreSQL 库运行，设置 `CATALOG_DB_TEST=true`；前端执行 `npm test` 和 `npm run build`。不要把测试密码、`.env` 或照片原件提交到仓库。
