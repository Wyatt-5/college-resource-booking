## 三种资源不要混在一起

| 资源 | 当前用途 | 数据与代码 |
| --- | --- | --- |
| 存放地点 | 三间办公室、一间物资室；物品归属在这里，地点本身不预约 | `location/`、V1/V2 迁移、`GET /api/v1/locations` |
| 物品和实物 | 物品有名称、介绍、照片、贵重标记、借用规则；一条物品可有多件带编号的实物 | `catalog/`、V3/V4 迁移；数量由 `item_units` 计算 |
| 可预约地点 | 目前预置两间会议室；以后可新增活动地点，跟存放地点是两类数据 | `booking/SpaceController`、`SpaceService`、V7 迁移 |

## 当前本地已有的入口

以下路径都以 `/api/v1` 开头。`POST /reservations` 同时接物品 `ITEM` 和可预约地点 `SPACE`，请求用 `resourceType` 区分。

| 功能 | 主要接口 | 现在的状态 |
| --- | --- | --- |
| 登录和账号 | `GET /auth/csrf`、`POST /auth/login`、`GET /auth/me`、`POST /auth/logout`、`GET/POST /users`、`PUT /users/{id}/grants` | 真实会话登录已接；目前只有系统管理员可建账号及改授权 |
| 物品 | `GET/POST /items`、`GET/PATCH /items/{id}`、`GET /items/{id}/units`、`PUT /items/{id}/stock` | 浏览、上架、编辑和设置库存已有；调整库存时由后端生成新增实物编号 |
| 物品照片 | `GET/POST /items/{id}/images`、`GET/DELETE /items/{id}/images/{imageId}` | 上传、读取和删除已有；读取权限由后端控制 |
| 可预约地点 | `GET/POST /spaces`、`GET /spaces/{id}/slots?date=...`、`GET/POST /spaces/{id}/image` | 浏览、新增、照片和时段查询已有；**编辑已有地点尚未实现** |
| 预约与审批 | `POST /reservations`、`GET /me/reservations`、`DELETE /me/reservations/{id}`、`GET /review/reservations`、`PATCH /reservations/{id}/review` | 物品、地点预约与单人审批已在本地实现；申请人不能自审 |
| 时段与日志 | `GET /items/{id}/availability?date=...`、`GET /management/reservations` | 物品时段表、管理预约记录已有；预约列表目前未直接显示审核人 |
| 归还核验 | `GET /reservations?status=RETURN_SUBMITTED`、`POST /reservations/{id}/return-verification` | 有核验接口外壳；预约模块还没接入真实归还数据，不能作为完成的借还流程 |

## 现在的预约规则

- 普通物品在库存和时段允许时返回 `CONFIRMED`；贵重物品和可预约地点先返回 `PENDING_APPROVAL`。审核通过时再次检查冲突，不能靠页面上的“空闲”提示代替后端检查。
- 同一物品按后端事务锁检查重叠时段；同一可预约地点不能出现两个相同时段的已确认申请。创建请求要带 `Idempotency-Key`，避免重复提交。
- 物品预约按整点选择，可以跨天；具体提前天数和最长借用天数由物品规则控制。地点预约限未来一周、同一天、08:00–22:00 的整点时段。
- `unitSummary.available` 表示当前状态为 `AVAILABLE` 的实物数量，**不等于任意未来时段的可预约量**；选好时间后要查时段表，提交时后端再判断。
- 目前地点审核会阻止审核者在重叠的辅导员待审申请之前批准学生。这和“辅导员可决定把资源给学生”的目标不一致，列入[本周分工](2026-11-02至11-08任务分工.md)，不能说已经解决。
