# 共用物品预约与借还系统：八周开发分工与验收清单

> 适用仓库：`college-resource-booking`。本文是六人小组的建议执行版，组长可直接分配 GitHub Issue。所有路径均相对仓库根目录；“新增”表示当前骨架尚无该文件或目录。第 1 周从正式开工日计算，每周末进行一次全组验收。

## 一、八周目标和功能边界

| 阶段 | 截止结果 |
|---|---|
| 第 1–4 周：功能开发 | 第 4 周末在测试环境完整演示：登录 → 浏览/上架物品及照片 → 预约 → 必要时单人审批 → 确认取件 → 上传照片和可选备注提交归还 → 管理员核验；会议室完成独立预约、审核、冲突处理和辅导员优先规则；操作均可追溯。独立任务服务可在本地调用核心 API。 |
| 第 5–8 周：验收交付 | 修复测试发现的问题；完成手机与电脑验收、跨两台机器运行、HTTPS 测试部署、备份恢复、课程报告/演示/讨论和成员贡献记录。第 5 周起原则上不新增业务功能，只修缺陷和完成部署。 |

初始数据为 3 间办公室、1 间物资室、2 间会议室、6 位辅导员、10 位学生组织负责人。这些**数量和具体人员是数据，不写死在代码里**。物品可有多个唯一编号的实物；贵重标记由管理员设置；贵重物品及会议室须审批；任一有权且非申请人的审核员同意即可。物品按服务端提交顺序竞争名额；会议室待审申请中辅导员优先，已确认预约只可经过有理由、有通知、有日志的显式处理。用户现场确认取件；归还至少上传一张照片，可写备注，管理员核验后才释放实物。

## 三、谁先做、谁等谁：真实依赖

**开工当天六个人都能动手。** 第 1–2 天必须全组确定首批资源字段、预约状态、角色权限和接口请求/响应示例；这份契约是联调依据。前端页面先按契约使用模拟响应，后端各自建模块和测试。等的是某个**接口或数据结构**，不是等某个人把全部工作做完。

| 人 | 现在就做，不等别人 | 真正需要等待的交付物 | 交付后解锁谁 |
|---|---|---|---|
| **吴仪民** | 账号/角色表与登录契约、审计服务骨架、CI/环境说明；先给出“当前用户是谁、拥有什么权限”的响应示例。 | 受保护业务接口的最终联调，要等肖志和谢跃明交付各自接口；审计事件接入也要等他们发出业务动作。 | 登录和授权接口解锁侯梦豪登录联调及全部管理接口的权限联调；审计服务解锁肖志、谢跃明记录操作；内部服务身份解锁何俊辉 worker 联调。 |
| **肖志** | 地点/物品/实物编号/图片表、CRUD 和测试；这部分不依赖预约后端。 | 取件、归还和核验后端必须等谢跃明交付预约 ID、状态与“已确认且可取件”的接口/服务契约；正式鉴权接入等吴仪民权限接口。 | 物品与实物真实接口解锁李舒达上架联调、侯梦豪浏览联调，以及谢跃明按库存创建真实预约。取还件接口解锁侯梦豪归还页面和李舒达核验页面。 |
| **谢跃明** | 预约状态/并发测试设计、会议室表及日历、审批模型；可先用测试数据和模拟物品仓库开发。 | **物品真实预约**必须等肖志提供物品、可借实物和库存查询；权限/非自审的真实联调等吴仪民身份接口。会议室预约只需会议室基础数据，可先于物品预约完成。 | 预约创建与状态接口解锁侯梦豪“提交/我的预约”，并解锁肖志取还件；会议室/审批接口解锁何俊辉日历和审核台。 |
| **侯梦豪** | 用户页面、手机适配、登录/预约/取件/归还的表单与异常状态；根据已定 JSON 示例使用模拟响应。 | 登录真实联调等吴仪民；物品浏览等肖志；预约/我的预约等谢跃明；取件/归还等肖志。只等待对应接口，不等待所有后端完成。 | 用户端每接通一条真实流程，就给对应后端负责人反馈字段、状态和错误问题；第 4 周完整用户流程解锁全组验收。 |
| **李舒达** | 管理页面、上架/图片/编号/核验表单和桌面/手机样式；按契约使用模拟响应。 | 真实上架和库存联调等肖志物品接口；真实核验等肖志归还核验接口；管理员角色限制等吴仪民权限接口。 | 管理员“上架→编号→照片”和“归还核验”页面解锁整条端到端演示。 |
| **何俊辉** | 会议室日历/审核台页面与 worker 空工程、重试和日志框架；模拟响应可先运行。 | 会议室/审核台真实联调等谢跃明；worker 真正处理任务等吴仪民的服务身份和谢跃明的到期/逾期任务接口或事件。 | 会议室页面解锁房间流程验收；worker 独立调用核心 API 解锁课程的两机子系统验收。 |

**最短的真实开发链：**

1. **第 1–2 天，全组同时开工**：吴仪民定身份/审计契约，肖志定物品/实物契约，谢跃明定预约/审批契约；侯梦豪、李舒达、何俊辉同步做各自页面和模拟数据。三对搭档当天确认字段，不等后端写完才问。
2. **第一条可验收链**：吴仪民交付登录/权限 → 肖志交付物品与实物 → 李舒达联调上架、侯梦豪联调浏览 → 谢跃明接上普通物品预约 → 侯梦豪联调提交和我的预约。
3. **第二条链**：谢跃明交付已确认预约及状态 → 肖志接上取件/归还/核验 → 侯梦豪接用户取还件、李舒达接管理员核验。
4. **会议室链可与物品链并行**：谢跃明先交付会议室、日历、审批 → 何俊辉接会议室页面与审核台；吴仪民交付服务身份且谢跃明交付内部任务接口后，何俊辉接 worker。无需等肖志完成所有物品功能。

**防止“接口接不上”的交付门槛：** 后端负责人说“接口好了”时，须同时提供 OpenAPI 路径和字段、一个成功请求/响应、至少一个失败响应、迁移文件和可运行的接口测试；前端负责人当天用真实接口替换该功能的模拟响应。字段不一致由这一对搭档共同修正，不交给组长单独补救。

## 四、每周任务清单：前四周完成全部功能

### 第 1 周：定规则、拆任务、搭可并行开发的骨架

- [ ] **吴仪民**：创建 `develop` 工作流程和 6 个模块 Issue；与全组定账号角色、权限范围、审计字段；提交账号/授权的数据模型与首批真实接口契约。
- [ ] **侯梦豪**：拆出用户端导航和页面组件；做登录、物品列表、我的预约的响应式页面骨架；用与 OpenAPI 一致的模拟数据，不把模拟成功当真实成功。
- [ ] **肖志**：盘点地点/物品/实物字段，设计图片元数据和实物状态；提交第一批新增迁移和物品读接口契约。
- [ ] **李舒达**：做物品详情、上架表单、图片上传、编号管理的页面原型与表单校验；同肖志确定字段。
- [ ] **谢跃明**：画物品与会议室预约状态图，确定服务端提交顺序、库存/时间冲突和禁止自审规则；提交预约/审批接口契约及最关键测试用例。
- [ ] **何俊辉**：做会议室日历与审核工作台的页面原型；画 worker → 核心 API 的跨机器调用图，并与吴仪民定内部接口/认证方式。

**第 1 周验收：** 全组各自在自己的电脑克隆、启动数据库/后端/前端并看到 4 个地点；OpenAPI 写明首批新增接口的请求、响应和错误；状态图及表关系由六人共同确认；每人至少有一个有验收条件的 Issue 和一项可审查的代码/契约提交。

### 第 2 周：完成真实账号、物品与普通预约的第一条闭环

- [ ] **吴仪民**：实现登录、当前身份、账号启停和角色授权最小闭环；写权限测试与审计写入基础能力。
- [ ] **侯梦豪**：把登录、物品浏览、我的预约和创建预约页面接到真实接口；显示 401/403/409 和加载状态。
- [ ] **肖志**：实现物品 CRUD、图片上传/受控读取、实物编号和可借状态，补迁移与测试；与李舒达联调上架到展示。
- [ ] **李舒达**：将上架/编辑、展示照片和库存编号页面接到真实接口；验证普通用户不能操作后台。
- [ ] **谢跃明**：实现普通物品预约、容量锁定/冲突处理、提交顺序；创建会议室基础数据和列表/日历接口；写同时抢同一资源的测试。
- [ ] **何俊辉**：会议室日历接入真实列表/占用接口；审核台接入真实队列的只读部分；搭建可独立启动的 worker 工程与核心 API 客户端。

**第 2 周验收：** 用真实账号完成“管理员上架一件有编号的物品及照片 → 普通用户浏览并预约”；两人抢最后一件库存只允许一个有效占用；普通用户无法调用后台写接口；会议室可在日历看到基础数据。

### 第 3 周：完成审批、取件、拍照归还及提醒逻辑

- [ ] **吴仪民**：完成可查询审计日志、审核小组/辅导员权限动态配置；给 worker 配独立服务身份和权限校验。
- [ ] **侯梦豪**：完成预约详情、取消、确认取件、拍照归还与备注页面；上传失败或网络重试时不产生重复提交。
- [ ] **肖志**：实现取件时绑定实物编号、用户提交归还照片、管理员接受/驳回核验；待核验实物不得再次预约。
- [ ] **李舒达**：完成归还核验后台、异常备注和照片查看；实测上架、停用、库存和核验操作。
- [ ] **谢跃明**：实现贵重物品/会议室单人审批、申请人禁止自审、会议室辅导员待审优先、显式覆盖已确认预约；补事务与规则测试。
- [ ] **何俊辉**：完成会议室预约和审核工作台的真实联调；worker 处理一次到期/逾期任务，记录结果，支持重试与防重复。

**第 3 周验收：** 用不同账号演示“贵重物品申请 → 非申请人审核 → 用户取件 → 上传照片归还 → 管理员核验”；会议室申请须审核，辅导员优先只改变待审顺序；关键动作在日志中可查；worker 可在本地独立启动并调用受保护接口。

### 第 4 周：补齐所有首版功能并冻结功能范围

- [ ] **吴仪民**：集成权限、审计、配置、错误码和部署参数；安排跨搭档代码审查；清理不能演示的占位按钮和模拟数据。
- [ ] **侯梦豪**：补齐用户端所有正常/失败状态，测试手机和电脑浏览器从登录到拍照归还的完整流程。
- [ ] **肖志**：修复照片/库存/交接边界问题；验证多件库存、停用实物、待核验归还；补真实数据库集成测试。
- [ ] **李舒达**：补齐管理员资源和核验页面，测试多管理员按授权范围操作；完成移动端后台可用性。
- [ ] **谢跃明**：完成预约取消、时段变更/覆盖、审批重复点击和并发压力下的一致性；补会议室日历、黑名单时段及审批测试。
- [ ] **何俊辉**：完成 worker 的失败重试和处理日志；补齐会议室/审核台异常状态，编写两机部署步骤。

**第 4 周验收＝功能开发完成：** 全组从页面实际走通物品和会议室两条完整流程；4 类关键账号（普通用户、辅导员、学生审核员、资源管理员）按授权操作；先提交者优先、单人非自审、会议室优先、归还必传照片、多件编号、日志均有测试或演示证据。仍未接通的首版功能不得标“完成”。

## 六、每周固定协作规则

1. **周一**：15–30 分钟定本周验收场景，建立/更新 GitHub Issue；接口请求和响应先写入 `contracts/openapi/openapi.yaml`。
2. **周二至周四**：从最新 `develop` 建 `feature/<issue号>-<名称>` 分支；后端和前端搭档并行开发，单项任务尽量 1–3 天可合并。页面可先用契约一致的模拟数据，但不能把模拟数据提交为“真实已联调”。
3. **周五**：提交 PR，写明测试方法、接口变化、迁移文件、截图/响应；另一位非作者组员审查，CI 通过后合到 `develop`。
4. **周末验收**：六人共同运行一条真实流程，记录通过/失败、截图/日志和负责人。验收通过的版本由 `develop` 经 PR 合到 `main`；未完成任务留在下一周 Issue，不在演示中假称完成。
5. **共享文件冲突**：`App.vue` 导航由侯梦豪合入；`openapi.yaml` 由该功能前后端共同维护；数据库迁移编号由吴仪民登记；每个模块负责人自己修本模块故障，不让组长代替写完。

**每项功能的“完成”定义：** 真实数据库和真实接口可用；对应页面在手机/电脑可操作；无权限、冲突、重复提交时行为正确；关键状态有自动测试；操作日志可查；OpenAPI、迁移和启动文档随代码更新；另一位组员能独立复现。仅有页面截图或接口空壳不算完成。
