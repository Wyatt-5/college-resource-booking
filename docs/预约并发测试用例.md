## 1. 硬性技术规范（违反则测试无效）

这一节比下面的用例更重要。并发测试最容易出现"测试通过但代码是错的"，全部原因都在这里。

### 1.1 绝不加 `@Transactional`

```java
// 错误：测试方法上的 @Transactional 让整个方法在单个事务里跑，
// 多线程各自开自己的连接，看不到测试事务未提交的数据 → 断言恒真 → 假通过
@SpringBootTest
@Transactional          // ← 删掉
class ReservationConcurrencyTest { }
```

用 `@BeforeEach` 清表代替回滚：

```java
@BeforeEach
void cleanUp() {
    jdbc.execute("TRUNCATE reservation_idempotency, approval_records, reservations RESTART IDENTITY CASCADE");
    // 只清本模块的表；地点/物品基础数据由各用例自己插
}
```

> 表名以预约模块的建表迁移为准，若实现时调整，同步改本节和 1.6。
>
> **迁移编号已变更**：物品模块的 PR #5 已占用 `V3__create_catalog.sql` 与 `V4__align_catalog_contract_and_add_audit.sql`，预约模块的迁移排在 **`V5`**（PR #5 合入 `develop` 后）。若合并顺序变化，以 `develop` 上 `db/migration` 的最大编号 + 1 为准，不要写死。

### 1.2 并发必须"同时起跑"，不能 for 循环顺序调用

```java
int threads = 2;
var ready = new CountDownLatch(threads);   // 全员就位
var start = new CountDownLatch(1);         // 发令枪
var results = Collections.synchronizedList(new ArrayList<Result>());
var pool = Executors.newFixedThreadPool(threads);
try {
    for (int i = 0; i < threads; i++) {
        pool.submit(() -> {
            ready.countDown();
            start.await();                 // 卡在这里，等所有人到齐
            results.add(post("/api/v1/reservations", body));
            return null;
        });
    }
    assertThat(ready.await(5, TimeUnit.SECONDS)).isTrue();
    start.countDown();                     // 一起放行
    pool.shutdown();
    assertThat(pool.awaitTermination(30, TimeUnit.SECONDS)).isTrue();
} finally {
    pool.shutdownNow();
}
```

两个 `CountDownLatch` 缺一不可：只用一个 `start` 闸，先到的线程可能已经跑完，后到的才开始，根本不是并发。**顺序执行时用例 1 也会"通过"**，但它证明不了任何东西。

### 1.3 断言必须落到数据库，不能只看 HTTP 响应

响应码正确但库里写了两条，是最典型的漏测。每条并发用例都要补一句"库里到底有几条"：

```java
Integer confirmed = jdbc.queryForObject("""
    SELECT count(*) FROM reservations
     WHERE room_id = ? AND status = 'CONFIRMED'
    """, Integer.class, roomId);
assertThat(confirmed).isEqualTo(1);
```

### 1.4 时间窗用相对时间，不硬编码

```java
// 好：相对当前时间，永远在"可预约范围内"
Instant startAt = Instant.now().plus(72, ChronoUnit.HOURS).truncatedTo(ChronoUnit.HOURS);
Instant endAt   = startAt.plus(1, ChronoUnit.HOURS);

// 坏：写死 2026-11-10 09:00，过了那天全部用例因"提前天数超限"而 400
```

同一用例内的所有请求**必须共用同一个 `startAt`**，否则"同一时段"这个前提就不成立。

### 1.5 测试类之间不要并行

`src/test/resources/junit-platform.properties`：

```properties
junit.jupiter.execution.parallel.enabled=false
```

并发用例内部自己开线程；JUnit 再并行跑测试类，两条用例会互相 `TRUNCATE` 对方的表，出现随机失败。

### 1.6 认证接缝（依赖 1 号的 auth 模块）

并发用例需要"以不同身份发请求"，但 auth 还没交付。**不要**在业务代码里加 `X-Test-User` 之类的后门。约定一个接口，测试里替换实现：

```java
public interface CurrentUserProvider {          // 生产实现读会话
    AuthUser current();
}

@TestConfiguration
class FixedUserConfig {
    @Bean @Primary
    CurrentUserProvider fixedUser() { return () -> AuthUser.of(USER_ID, Role.USER); }
}
```

需要切换身份时用 `@MockitoBean CurrentUserProvider`，在测试方法里 `given(provider.current()).willReturn(...)`。这条要写进与 1 号的接口约定。

### 1.7 每条用例自建数据

不依赖 `V2__seed_known_locations.sql` 的 4 条地点，也不用固定 id。每例开头自己插资源，拿到 `id` 再往下走：

```sql
INSERT INTO rooms (location_id, name, status) VALUES (?, '测试会议室 A', 'ACTIVE') RETURNING id;
-- 物品模块的 items 没有 capacity 列：可借数量 = item_units 中状态为 AVAILABLE 的行数
INSERT INTO items (location_id, name, is_valuable, status) VALUES (?, '测试投影仪', false, 'ACTIVE') RETURNING id;
INSERT INTO item_units (item_id, unit_code, status) VALUES (:itemId, 'T-001', 'AVAILABLE'),
                                                          (:itemId, 'T-002', 'AVAILABLE');
```

字段名以 `V3__create_catalog.sql` 为准（`is_valuable` 不是 `valuable`，没有 `capacity` 列）。

### 1.8 与物品模块的字段与状态对齐（写用例前必须先看）

物品模块的 PR #5（`feature/catalog-read`）已经落了三张表，预约模块只能引用、不能改：

| 表 | 可用列 | 预约模块怎么用 |
|---|---|---|
| `items` | `id, location_id, name, description, is_valuable, status, max_advance_days, max_borrow_days, max_borrow_hours` | **没有 `capacity`**。可借数量 = `item_units` 中 `status='AVAILABLE'` 的行数 |
| `item_units` | `id, item_id, unit_code, status`（`AVAILABLE / CHECKED_OUT / RETURN_SUBMITTED / MAINTENANCE / DISABLED / LOST`） | 取件时绑定具体 `unit_id`；`(item_id, unit_code)` 唯一 |
| `item_images` | `id, item_id, storage_key, content_type, size_bytes, width, height, sort_order, file_name` | 归还核验的照片走他们的接口，预约模块不建照片表 |

两个必须写进接口约定的点：

1. **容量是派生的，不是列。** `SUM(quantity) <= capacity` 里的 `capacity` 必须替换成「该物品 `AVAILABLE` 实物数」。好处是：`quantity` 可以校验 `<= 可借实物数`，同时 `EXCLUDE (unit_id, tstzrange)` 才有可能落地——如果预约能锁定到具体 `unit_id`，物品也能用排他约束，连锁都不用加（见状态图 5.2）。
2. **`item_units.status` 与 `reservations.handover_status` 是同一个事实的两份记录。** 3 号已把 `CHECKED_OUT`、`RETURN_SUBMITTED` 写进 `item_units.status` 的 CHECK 约束。必须约定**唯一写入方**：建议 `reservations.handover_status` 为权威源，`item_units.status` 由 booking 模块在同一事务内同步（取件→`CHECKED_OUT`，核验通过→`AVAILABLE`）。否则两处各改一处，盘点必然对不上。

另外 3 号已经在 `catalog` 包里定义了 **`ReservationReturnGateway`**，注释写明「Implemented by booking module in the SAME datasource/transaction」，这是预约模块**必须实现**的接口：

```java
ReturnRecord lock(long reservationId);                                   // 锁定预约并校验 item/unit 绑定不可变
List<ReturnRecord> queue(CatalogAccess.Actor actor, int page, int size);  // 归还核验队列（对应 /reservations/return-queue）
void finish(long reservationId, String status, String actor, String reason); // 原子写核验人与理由并迁移状态
```

用例 2、3 的「容量」、以及归还相关的断言，都受这张表约束，写代码前先按它对齐。

## 3. 并发与一致性

### 用例 1 — 同一会议室同一时段两人并发申请

| 项 | 内容 |
|---|---|
| 前置 | 1 间会议室（同一时段只能被 1 条 `CONFIRMED` 占用）；用户 A、B 各一条会话 |
| 操作 | A、B 同时 `POST /reservations`，`resourceType=ROOM`、同一 `resourceId`、同一 `[startAt, endAt)`；不加 `Idempotency-Key`（这是两次真实意图） |
| 期望 | 恰好 1 个 `201` 且 `status=CONFIRMED`；另 1 个 `409` 且 `code=RESOURCE_CONFLICT` |

```sql
-- 断言 1：只有一条 CONFIRMED
SELECT count(*) FROM reservations
 WHERE room_id = :roomId AND status = 'CONFIRMED'
   AND tstzrange(start_at, end_at, '[)') && tstzrange(:startAt, :endAt, '[)');   -- 期望 1

-- 断言 2：失败的请求没有留下垃圾行
SELECT count(*) FROM reservations WHERE room_id = :roomId;                        -- 期望 1
```

**实现要点**：`EXCLUDE USING gist` 约束会在 commit 时抛 `SQLState 23P01`，映射为 `409 RESOURCE_CONFLICT`。第二个请求可能是"插入时被约束拒绝"（立即失败），也可能是"锁等待后失败"，两者都算通过 —— **不要断言失败方的响应时间**。

### 用例 2 — 库存 2，三条并发申请同一物品同一时段

| 项 | 内容 |
|---|---|
| 前置 | 1 个物品，`item_units` 里 2 件 `AVAILABLE` 实物（可借量 = 2）；用户 A、B、C |
| 操作 | 三人同时 `POST /reservations`，各 `quantity=1`，同一时段 |
| 期望 | 恰好 2 个 `201 CONFIRMED`；第 3 个为 `409 RESOURCE_CONFLICT`，或（若请求声明接受候补）`201 WAITLISTED` |

```sql
SELECT status, count(*) FROM reservations
 WHERE item_id = :itemId GROUP BY status ORDER BY status;
-- 期望：CONFIRMED = 2，且 WAITLISTED + CONFIRMED + (冲突未落库) 合计 3
```

**关键区分**：`WAITLISTED` **不占名额**（见状态图 5.2）。所以第 3 条若落库为 `WAITLISTED`，`CONFIRMED` 仍必须**恰好 2 条**，不能变成 3 条。这一条专门用来抓"把候补也算进容量"的错误实现。

### 用例 3 — 库存 1，两人并发

| 项 | 内容 |
|---|---|
| 前置 | 1 个物品，`item_units` 里 1 件 `AVAILABLE` 实物；用户 A、B |
| 操作 | 同时提交，各 `quantity=1` |
| 期望 | 恰好 1 个 `201`；另 1 个 `409 RESOURCE_CONFLICT` |

```sql
SELECT count(*) FROM reservations WHERE item_id = :itemId AND status = 'CONFIRMED';  -- 期望 1
```

**实现要点**：这是**唯一必须用咨询锁**的用例。会议室靠 `EXCLUDE`，物品容量是 `SUM(quantity) <= 可借实物数` 的聚合判断（`可借实物数` 来自 `item_units` 计数，`items` 没有 `capacity` 列），SQL 约束表达不了，必须在同一事务内 `pg_advisory_xact_lock(hashtextextended('ITEM:'||id,0))` 串行化后重算。

> 更好的做法（若取件能绑定到具体 `unit_id`）：物品也用 `EXCLUDE USING gist (unit_id WITH =, tstzrange(...) WITH &&)`，连锁都不用加。见状态图 5.2。

**反例（会挂在这里）**：

```java
int used = countUsed(itemId, start, end);   // 两人都读到 0
if (used + qty <= availableUnits(itemId)) insert();   // 两人都插入 → 超借
```

### 用例 4 — 两名审核员同时点"同意"

| 项 | 内容 |
|---|---|
| 前置 | 1 条会议室申请，`status=PENDING_APPROVAL`；两名有审核权限且**都非申请人**的审核员 R1、R2 |
| 操作 | 同时 `POST /reservations/{id}/decision`，`{decision:"APPROVE"}` |
| 期望 | 1 个 `200` 且 `status=CONFIRMED`；另 1 个 `409 INVALID_STATE`；审批表**只有 1 条** `APPROVE` 记录 |

```sql
SELECT count(*) FROM approval_records
 WHERE reservation_id = :id AND decision = 'APPROVE';      -- 期望 1

SELECT count(*) FROM reservations WHERE id = :id AND status = 'CONFIRMED';  -- 期望 1
```

**实现要点**：用条件更新一次判定，不要"先查后改"：

```sql
UPDATE reservations SET status = 'CONFIRMED', ...
 WHERE id = :id AND status = 'PENDING_APPROVAL';   -- 影响行数 0 → 409
```

响应恒为 `200`/`409` 之一，不能出现两个 `200`。

### 用例 5 — 同一 `Idempotency-Key` 提交两次

| 项 | 内容 |
|---|---|
| 前置 | 用户 A，一个固定 key `8f3a1c9e-...` |
| 操作 | 用**同一 key、同一请求体**调两次 `POST /reservations`（并发或串行均可，两种都要跑） |
| 期望 | 两次返回**同一个 `id`**；库里只有 1 条预约、1 条幂等记录 |

```sql
SELECT count(*) FROM reservations WHERE applicant_id = :userId;                 -- 期望 1
SELECT count(*) FROM reservation_idempotency WHERE user_id = :userId;           -- 期望 1
```

**易错点**：断言的是"两次都成功且 `id` 相同"，**不是**"第二次返回 409"。幂等 = 重复请求得到相同结果；防重 = 拒绝第二次。前者对前端更友好，也是 `开发约束.md` 5.2 的要求。

补充一条负向断言（同一 key 换个请求体）→ `400 IDEMPOTENCY_KEY_REUSED`，这属于契约测试，可放在同一测试类的另一个方法里。

## 4. 时间冲突与边界

### 用例 6 — 相邻时段不算冲突

| 项 | 内容 |
|---|---|
| 前置 | 1 间会议室；用户 A、B |
| 操作 | A 订 `[09:00, 10:00)`；B 订 `[10:00, 11:00)` |
| 期望 | 两个都 `201 CONFIRMED` |

```sql
SELECT count(*) FROM reservations WHERE room_id = :roomId AND status = 'CONFIRMED';  -- 期望 2
```

**这一条专抓区间写法错误**。区间必须是左闭右开：

```sql
tstzrange(start_at, end_at, '[)')     -- 正确，10:00 端点不重叠
tstzrange(start_at, end_at, '[]')     -- 错误，用例 6 直接失败
```

同时补一条反向断言：`[09:00,10:00)` 与 `[09:30,10:30)` 必须冲突（否则说明约束压根没生效）。

### 用例 7 — 审批通过时容量已被他人占满

| 项 | 内容 |
|---|---|
| 前置 | 会议室一条 `PENDING_APPROVAL`（用户 A）；同间会议室同一时段已有一条 `CONFIRMED`（用户 B） |
| 操作 | 审核员对 A 的申请 `APPROVE` |
| 期望 | `409 RESOURCE_CONFLICT`；A 的预约**仍是 `PENDING_APPROVAL`**，不得自动转 `WAITLISTED` |

```sql
SELECT status FROM reservations WHERE id = :aId;      -- 期望 PENDING_APPROVAL
SELECT count(*) FROM approval_records WHERE reservation_id = :aId AND decision = 'APPROVE';  -- 期望 0
```

**为什么不能自动转候补**：审核员点的是"同意"，系统却把它变成"排队中"，审核员会以为自己批成功了。要让用户进候补，必须是用户自己重新提交并声明接受候补（那是一条新申请、新 `submission_seq`）。

## 5. 权限与业务规则

### 用例 8 — 申请人审批自己的申请

| 项 | 内容 |
|---|---|
| 前置 | 用户 A 既是申请人，又持有 `REVIEWER` 角色；一条 A 的 `PENDING_APPROVAL` |
| 操作 | A 对自己那条 `POST /{id}/decision` `APPROVE` |
| 期望 | `403 SELF_APPROVAL_FORBIDDEN`；预约仍 `PENDING_APPROVAL`；无审批记录 |

```sql
SELECT status FROM reservations WHERE id = :id;                              -- PENDING_APPROVAL
SELECT count(*) FROM approval_records WHERE reservation_id = :id;            -- 0
```

**易错点**：这里的 `403` 不是"你没权限审批"（那是 `FORBIDDEN`），而是"你有权限但不能审自己"。两个错误码语义不同，前端提示也不同：前者让用户找别人，后者让用户等别人。

再补一条：持有 `SYSTEM_ADMIN` 的人审自己的申请，同样 `403`（`开发约束.md` 2.2 原文："业务审批仍须遵守禁止自审规则"）。

### 用例 9 — 辅导员优先于普通用户

| 项 | 内容 |
|---|---|
| 前置 | 同间会议室、同一时段两条 `PENDING_APPROVAL`：普通用户 A **先提交**（`submission_seq` 小），辅导员 C **后提交**（`COUNSELOR_ADMIN`） |
| 操作 | 审核员查 `GET /approval-queue`；然后先批 C，再批 A |
| 期望 | 队列中 C 排在 A 前；C 批成功后 `CONFIRMED`；A 再批时 `409 RESOURCE_CONFLICT` |

```sql
SELECT id, applicant_id, priority_tier, submission_seq
  FROM reservations
 WHERE room_id = :roomId AND status = 'PENDING_APPROVAL'
 ORDER BY priority_tier, submission_seq;
-- 期望第一行是辅导员那条，且其 submission_seq 更大
```

**这一条同时验证 I4**：顺序由 `(priority_tier, submission_seq)` 决定，与"谁先被点开"无关。再补一条反向断言：先批 A（普通用户）会成功，之后 C 才是 `409` —— 说明优先级只影响**待审队列顺序**，不阻止审核员按自己意愿批。

> 备注：`priority_tier` 在提交时冻结（见状态图 D-5）。若实现改为实时判断角色，本用例要增加"提交后撤销角色，队列顺序不变"的断言。

### 用例 10 — 已确认会议室被辅导员 override

| 项 | 内容 |
|---|---|
| 前置 | 会议室一条 `CONFIRMED`（用户 A）；辅导员 C 提出同一时段申请 |
| 操作 | C 调 `POST /reservations/{aId}/override`，`{action:"CANCEL", reason:"学院临时会议"}` |
| 期望 | A 那条转 `OVERRIDDEN` 且 `reason` 落库；C 的预约 `CONFIRMED`；写审计；产生一条通知给 A |

```sql
SELECT status, override_reason FROM reservations WHERE id = :aId;   -- OVERRIDDEN / 非空
SELECT count(*) FROM reservations WHERE room_id = :roomId AND status = 'CONFIRMED';  -- 期望 1（C 那条）
SELECT count(*) FROM audit_logs WHERE target_id = :aId AND action = 'OVERRIDE';      -- 期望 1
SELECT count(*) FROM notifications WHERE user_id = :aUserId;                          -- ≥1
```

**最容易错的地方**：`OVERRIDDEN` 那条**不占名额**。如果容量谓词写成 `status IN ('CONFIRMED','OVERRIDDEN')`，这条用例会因为"同一时段占用 2 > 容量 1"而失败 —— 这正是状态图 5.1 要单独解释的原因。

**事务要求**：置 `OVERRIDDEN`、创建 C 的 `CONFIRMED`、写审计、发通知，四件事**必须同一事务**。分事务会出现"原预约已失效、新预约还没建"的空窗，此时别人可以抢走这个时段。

### 用例 11 — 普通用户访问审批队列

| 项 | 内容 |
|---|---|
| 前置 | 用户 A 仅 `USER` 角色 |
| 操作 | `GET /approval-queue` |
| 期望 | `403 FORBIDDEN` |

```java
// 断言响应体是统一错误格式，不是空列表
{"code":"FORBIDDEN","message":"...","details":{},"requestId":"..."}
```

**易错点**：返回 `200 []` 也算失败。空列表会让前端以为"没有待审"，而实际是"你没资格看"，语义完全不同。

### 用例 12 — 管理员越权查询

| 项 | 内容 |
|---|---|
| 前置 | 资源管理员 M 只被授权地点 L1；地点 L2 下有一条预约 |
| 操作 | M 调 `GET /reservations`（不带地点筛选） |
| 期望 | `200`，但结果中**不含** L2 的任何预约 |

```sql
SELECT count(*) FROM reservations r
  JOIN rooms rm ON rm.id = r.room_id
 WHERE rm.location_id = :l2Id AND r.id IN (:returnedIds);   -- 期望 0
```

**易错点**：这是"数据范围过滤"，不是"接口鉴权"。必须是查询条件里带 `location_id IN (授权范围)`，**不能**查完再在内存里过滤（分页会错位，总数会泄露）。

### 用例 13 — 非法状态迁移

| 项 | 内容 |
|---|---|
| 前置 | 一条 `CANCELLED` 的预约 |
| 操作 | 对该条 `POST /{id}/decision` `APPROVE` |
| 期望 | `409 INVALID_STATE`；状态不变 |

参数化遍历所有非法边（状态图 6.3）：

| 起始状态 | 非法动作 | 期望 |
|---|---|---|
| `CANCELLED` | `APPROVE` | `409 INVALID_STATE` |
| `REJECTED` | `APPROVE` | `409 INVALID_STATE` |
| `EXPIRED` | `APPROVE` | `409 INVALID_STATE` |
| `CONFIRMED` + `CHECKED_OUT` | `cancel` | `409 INVALID_STATE` |
| `PENDING_APPROVAL` | `pickup` | `409 INVALID_STATE` |
| `WAITLISTED` | `pickup` | `409 INVALID_STATE` |

```sql
SELECT count(*) FROM reservations WHERE id = :id AND status = :unchangedStatus;  -- 期望 1
```

**实现要点**：用 `@ParameterizedTest` + `@CsvSource` 一行一条，不要写六个方法。

### 用例 14 — 提前天数 / 最长时长超限

| 项 | 内容 |
|---|---|
| 前置 | 配置：最多提前 14 天、单次最长 4 小时 |
| 操作 | ① `startAt = now()+21d`；② `endAt = startAt+6h` |
| 期望 | 均 `400 VALIDATION_ERROR`，`details` 的 key 是对应字段名 |

```json
{"code":"VALIDATION_ERROR",
 "message":"预约时间不满足规则",
 "details":{"startAt":"最多提前 14 天，实际 21 天",
            "endAt":"单次最长 4 小时，实际 6 小时"},

```

**注意**：这两项必须来自配置或资源字段（`开发约束.md` 开篇明确"不能散落为硬编码常量"）。测试里通过 `@TestPropertySource` 覆盖成小值，别依赖生产默认值。

## 6. 候补与脱敏

### 用例 15 — 确认预约被取消后候补按顺位转正

| 项 | 内容 |
|---|---|
| 前置 | 会议室容量 1；A 已 `CONFIRMED`；B、C 先后进 `WAITLISTED`（B 的 `submission_seq` 更小） |
| 操作 | A 调 `POST /{aId}/cancel` |
| 期望 | A → `CANCELLED`；**B → `CONFIRMED`**；C 仍 `WAITLISTED`；三步同一事务 |

```sql
SELECT id, status FROM reservations WHERE room_id = :roomId ORDER BY submission_seq;
-- 期望：A=CANCELLED, B=CONFIRMED, C=WAITLISTED
```

**事务断言怎么做**：`@Transactional` 会掩盖问题（见 1.1）。改用"故障注入"验证原子性 —— 让通知写入故意抛异常，断言 A 也**没有**变成 `CANCELLED`：

```java
assertThatThrownBy(() -> service.cancel(aId)).isInstanceOf(...);
// 断言：整笔回滚，A 仍 CONFIRMED，B 仍 WAITLISTED
```

这条比"结果对不对"更能证明事务边界，也是答辩时的加分点。

**不依赖 worker**：转正由取消方在同一事务内完成（状态图 I5）。若实现依赖定时任务，B 会短暂停留 `WAITLISTED`，本用例会失败 —— 这是**有意的**。

### 用例 16 — 会议室日历脱敏

| 项 | 内容 |
|---|---|
| 前置 | 会议室有一条 `CONFIRMED`，申请人是用户 A，`purpose="学生会例会"` |
| 操作 | 用户 B 调 `GET /rooms/{id}/calendar?from=...&to=...` |
| 期望 | `200`，该时段标记为已占用，但**不含** A 的姓名、学号、`purpose`、预约 `id` |

```json
{"roomId":1,"slots":[{"startAt":"...","endAt":"...","occupied":true}]}
```

正向断言可以直接检响应体字符串不含敏感词：

```java
assertThat(body).doesNotContain("学生会例会").doesNotContain(applicantName);
```

**为什么要单独测**：日历是公开页面，一旦返回 `applicantName`，等于把"谁什么时候在哪个会议室"全暴露。`开发约束.md` 要求"图片访问须受权限控制"体现的也是同一个原则：权限不是按钮，是数据。

## 7. 测试类骨架（可直接抄）

```java
package edu.college.booking;

import static org.assertj.core.api.Assertions.assertThat;

import java.time.Instant;
import java.time.temporal.ChronoUnit;
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;
import java.util.concurrent.CountDownLatch;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.Timeout;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.test.web.client.TestRestTemplate;
import org.springframework.jdbc.core.JdbcTemplate;

@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class ReservationConcurrencyTest {          // 注意：类上不加 @Transactional

    @Autowired TestRestTemplate http;
    @Autowired JdbcTemplate jdbc;

    long roomId;
    Instant startAt;
    Instant endAt;

    @BeforeEach
    void setUp() {
        jdbc.execute("TRUNCATE reservation_idempotency, approval_records, reservations RESTART IDENTITY CASCADE");
        roomId = jdbc.queryForObject("""
            INSERT INTO rooms (location_id, name, status) VALUES (?, ?, 'ACTIVE') RETURNING id
            """, Long.class, locationId(), "测试会议室 A");
        startAt = Instant.now().plus(72, ChronoUnit.HOURS).truncatedTo(ChronoUnit.HOURS);
        endAt = startAt.plus(1, ChronoUnit.HOURS);
    }

    @Test
    @Timeout(60)
    void twoConcurrentRoomRequestsOnlyOneWins() throws Exception {
        List<Response> results = runConcurrently(2, () -> postRoomReservation(roomId, startAt, endAt));

        assertThat(results).filteredOn(r -> r.status == 201).hasSize(1);
        assertThat(results).filteredOn(r -> r.status == 409).hasSize(1);
        assertThat(confirmedCount(roomId)).isEqualTo(1);
    }

    private List<Response> runConcurrently(int threads, ThrowingSupplier<Response> action) throws Exception {
        var ready = new CountDownLatch(threads);
        var start = new CountDownLatch(1);
        var results = Collections.synchronizedList(new ArrayList<Response>());
        ExecutorService pool = Executors.newFixedThreadPool(threads);
        try {
            for (int i = 0; i < threads; i++) {
                pool.submit(() -> {
                    ready.countDown();
                    start.await();
                    results.add(action.get());
                    return null;
                });
            }
            assertThat(ready.await(10, TimeUnit.SECONDS)).isTrue();
            start.countDown();
            pool.shutdown();
            assertThat(pool.awaitTermination(30, TimeUnit.SECONDS)).isTrue();
        } finally {
            pool.shutdownNow();
        }
        return results;
    }

    private int confirmedCount(long roomId) {
        return jdbc.queryForObject(
            "SELECT count(*) FROM reservations WHERE room_id = ? AND status = 'CONFIRMED'",
            Integer.class, roomId);
    }
}
```

## 9. 六个"假通过"陷阱

| 陷阱 | 现象 | 后果 |
|---|---|---|
| 测试类加了 `@Transactional` | 永远绿 | 并发根本没被验证（1.1） |
| 只有一个 `CountDownLatch` | 时绿时红 | 顺序执行，用例 1 变成普通插入测试（1.2） |
| 只断言 HTTP 码，不查库 | 绿 | 可能写了 2 条、只是响应返回了 409（1.3） |
| 用例间共用固定 id | 随机失败 | 并行/顺序不同导致脏数据互相干扰（1.5 + 1.7） |
| 断言失败方"一定先报约束异常" | 偶发红 | 物品那条走的是锁等待，报错路径和会议室不同（用例 1 备注） |
| 候补转正靠 sleep 后再查 | 偶发红 | 说明实现依赖异步任务，本该同事务（用例 15） |
