# 共用资源预约与借还系统：开发约束与接口约定（v1.0）

> 供六人小组放入 GitHub 仓库的 `docs/` 目录。日期：2026-10-25。本文是开发基线；业务规则改变时先修改本文和接口契约，再改代码。文中的“建议默认值”可由学院确认后调整。

## 1. 项目边界与验收目标

系统面向学院内部使用，支持手机、电脑浏览器和管理后台。第一版采用响应式 Web 页面；不同时开发原生 Android、iOS 客户端。课程要求的主体程序使用面向对象的主流语言，建议后端采用 Java；须展示多个运行在**不同机器**上的分布式子系统，并在 8–10 周内完成可演示、可试用的闭环。

首版必须跑通：账号登录 → 查看资源 → 预约 → 必要时审核 → 取件 → 使用 → 拍照提交归还 → 管理员核验；会议室则跑通预约、审核、取消和到期结束。照片上传、多管理员、操作日志、并发冲突处理、部署说明和备份恢复属于首版，不放到“有空再做”。支付、押金、微信小程序、复杂推荐算法暂不纳入首版。

**待学院确认而不影响先开发的规则**：预约可提前多少天、单次最长借用时长、审批超时多久自动失效、逾期多久提醒、哪些物品属于贵重物品。这些须做成配置或资源字段，不能散落为硬编码常量。

## 2. 资源模型与权限

### 2.1 资源层级

| 类型 | 初始数据 | 规则 |
|---|---:|---|
| 存放地点 `Location` | 3 间办公室、1 间物资室 | 作为物品的上级分类；第一版不预约地点本身。地点数量可增加。 |
| 物品 `Item` | 按实际盘点录入 | 归属一个地点；有名称、介绍、照片、是否贵重、可借规则、启停状态。 |
| 实物 `ItemUnit` | 每件库存一条记录 | 有唯一编号、所属物品、当前状态；预约按数量占名额，交接时绑定具体编号。 |
| 会议室 `Room` | 2 间 | 独立可预约资源，有容量、地点、开放时间、停用时段。 |

不得把“三间办公室、两间会议室、六位辅导员、十位负责人”写死进枚举或判断语句；这些只是上线初始数据。

### 2.2 账号、角色与授权

- `USER`：浏览、预约、取消本人申请、确认取件、提交归还照片及备注。
- `COUNSELOR_ADMIN`：六位辅导员初始拥有管理权限，可管理资源、设置贵重标记、处理异常和会议室优先占用。后续通过授权配置增减人员。
- `RESOURCE_MANAGER`：负责指定地点或物品的上架、库存、取还件核验。授权范围按资源记录，不按姓名写代码。
- `REVIEWER`：十位学生组织负责人初始加入审核小组；人员增减通过后台配置。可以同时具有其他角色。
- `SYSTEM_ADMIN`：少量系统维护人员，负责账号启停、角色授权、系统配置。业务审批仍须遵守禁止自审规则。

管理权限与审核权限分开；六位辅导员是否同时加入常规审核小组，由学院在后台授权。贵重物品和会议室的**一份申请只需一名有权审核的人同意**。申请人不能审核自己的申请，即使其拥有多个角色。授权变更不改写历史日志。

后端必须逐接口校验权限与资源范围；隐藏按钮不等于完成鉴权。所有增删改和审批动作都记录操作者、时间、对象、动作、结果及必要的前后状态。

## 3. 业务状态与调度规则

### 3.1 预约状态

统一预约主状态：`PENDING_APPROVAL`（待审核）、`WAITLISTED`（冲突候补）、`CONFIRMED`（已占用名额）、`REJECTED`、`CANCELLED`、`EXPIRED`、`OVERRIDDEN`（有原因的优先占用）。物品在确认后增加交接状态：`NOT_PICKED_UP`、`CHECKED_OUT`、`RETURN_SUBMITTED`、`RETURN_REJECTED`、`COMPLETED`。会议室在使用时段结束后为 `COMPLETED`，不使用取件/归还状态。

- 普通物品：有容量且无更早的有效冲突申请时自动 `CONFIRMED`；否则返回冲突或明确进入 `WAITLISTED`，不得假称预约成功。
- 贵重物品：提交后 `PENDING_APPROVAL`；一个非申请人的审核员同意后，后端**重新检查冲突和容量**，成功才转 `CONFIRMED`。拒绝则 `REJECTED`。
- 会议室：提交后 `PENDING_APPROVAL`；同样一人审核，但辅导员的待审核申请优先于普通用户。同级别按服务器认定的提交顺序。
- 已确认的预约不能被系统静默挤掉。辅导员确需优先占用已确认会议室时，须填写原因并执行显式改期或取消，通知原预约人，写入 `OVERRIDDEN` 与审计日志。
- 申请待审超时、用户取消或审核拒绝后，释放候补顺位。超时时长为后台配置。贵重标记变更只影响新申请；已有申请按创建时的规则处理。

### 3.2 “先提交者优先”的精确定义

客户端时间不参与排序。后端在接收并持久化申请时分配不可修改的 `submitted_at` 和单调递增的 `submission_seq`；排序先看适用的业务优先级，再看 `submission_seq`。同一时段内，物品按先提交优先；会议室待审队列中辅导员优先，同一身份层级再按提交顺序。不得用审批员点击按钮的时间改变既定顺位。

预约创建、审核通过、取消和超时释放都须在数据库事务中执行容量与时间冲突检查。对同一资源的并发操作要串行化或使用数据库约束，不能“先查询空闲、再无保护地插入”。会议室容量始终为 1；多件库存物品的同一时段确认数不能超过可借实物数。已逾期未归还或待归还核验的实物不得重新分配。未能取得名额的请求返回 `409 RESOURCE_CONFLICT` 或明确的 `WAITLISTED` 状态。

### 3.3 取件和归还

预约 `CONFIRMED` 后，用户现场拿到物品，点击“确认取件”，由后端记录取件时间并绑定具体实物编号；未到可取件时间、无可交付实物或状态不符时拒绝。归还时用户必须上传至少一张现场照片，可填写备注，然后进入 `RETURN_SUBMITTED`。有权限的管理员核对实物，可确认归还并使实物重新可借，也可驳回并写明原因，维持占用。双方操作和图片关联关系均进入审计记录。

### 3.4 审批与日志

审批记录独立于预约主表：记录审核人、同意/拒绝、理由、时间、当时的授权范围。单人同意即完成审批；重复点击须幂等，不能产生两个有效结果。日志至少覆盖账号与授权变更、资源变更、预约创建/取消、审批、优先占用、取件、归还提交与核验；普通管理员不可修改或删除审计日志。

## 4. GitHub 仓库与分支约束

### 4.1 一个仓库，多个模块

首版只建**一个 GitHub 仓库**，避免六个人在多个仓库间追逐接口版本。“每个仓库的接口”在本项目中落实为“每个模块的接口”。目录建议：

```text
frontend/          # 用户端和管理后台，同一 Web 工程
backend/           # Java 核心 API：用户、物品、预约、审核、日志
worker/            # 独立运行的逾期、超时与提醒子系统
contracts/openapi/ # 唯一的 HTTP 接口契约
db/migrations/     # 有版本号的数据库迁移
infra/             # 本地启动、部署、反向代理与备份脚本
docs/              # 需求、状态图、架构图、测试和运维手册
.github/workflows/ # 自动构建与测试
```

前端只通过 `/api/v1` 调后端，不直接连接数据库。`worker` 部署在另一台机器，使用专用服务身份与核心 API 通信；不得直接修改核心数据库。课程演示应展示两台机器的地址、运行进程、任务调用和日志。开发时可单机运行，但验收前必须完成跨机器验证。

### 4.2 分支数量与命名

- **长期分支固定 2 条**：`main` 为可演示/可部署版本；`develop` 为日常集成版本。
- **短期分支按任务建立**：`feature/<issue号>-<简述>`、`fix/<issue号>-<简述>`、`docs/<issue号>-<简述>`。不建六条永久的个人分支。
- 建议同一时间保留 **3–6 条短期分支**；一项功能完成就合并并删除，不为了凑数量建分支。一个任务尽量在 1–3 天内能合并。
- 功能分支从最新 `develop` 建立，Pull Request 合并回 `develop`；每周从通过验收的 `develop` 向 `main` 提交一次发布 PR。紧急修复从 `main` 建 `fix/...`，完成后同步回 `develop`。
- 保护 `main` 和 `develop`：禁止直接推送和强制推送；合并须至少 **1 名其他组员**审查、自动构建/测试通过、冲突解决。业务上的“单人审批”与 GitHub 代码审查是两件不同的事。

每个 GitHub Issue 写清用户故事、验收条件、负责人和接口影响；每个 PR 写改了什么、关联 Issue、如何测试、界面截图或接口示例、是否有数据库迁移。修改接口或状态时，同一个 PR 必须更新 `contracts/openapi/` 和相关文档。数据库结构只能经迁移脚本变更，不在共享环境手工改表。主分支的密钥、照片和真实个人数据不得提交到 GitHub。

## 5. API 总约定

**注意：下表是拟定的接口清单，不代表这些接口已经实现或现在就能调用。** 第一周由前后端共同确认路径、字段、状态和示例响应，写入 OpenAPI；实现过程在任务看板中分别标记 `已约定`、`模拟可用`、`真实实现`、`联调通过`。前端只能把“联调通过”视为真实可用。

路径定下后前后端不能各自更名。所有路径以 `/api/v1` 为前缀。采用 JSON；图片上传使用 `multipart/form-data`。请求和响应字段采用 `camelCase`，ID 为不可复用标识，列表统一支持 `page`、`size` 和必要的筛选参数。时间传 ISO 8601，服务端统一存 UTC，界面按 `Asia/Shanghai` 显示；预约时段使用 `[startAt, endAt)`，即结束时刻不占用下一段的开始时刻。

### 5.0 先约定接口，再并行实现

“接口地址”由**服务器地址 + 端口 + 路径**组成，例如本机开发时 `http://localhost:8080/api/v1/items`。其中 `/api/v1/items` 是前后端应共同遵守的接口路径；`8080` 只是某台开发机器上的监听端口，可以通过配置改变。数据库的 `5432` 等端口只供后端连接，前端不能直接连接数据库。

推荐按以下顺序推进，而不是由组长先建完所有数据库、开放所有真实接口，其他人才开始工作：

1. **全组定需求和契约**：各搭档一起定状态图、核心字段、API 路径、请求/响应示例及错误码；接口文档由对应模块的前后端共同负责。
2. **你建立最小骨架**：跑通一个 `/api/v1/health`、数据库连接、第一版迁移脚本、登录基础、统一错误格式；把启动命令和测试账号写入 README。
3. **各搭档并行实现**：前端先使用与 OpenAPI 相同的模拟响应或后端返回的临时固定响应；后端同时建该模块的表和业务逻辑。数据库可按模块增量迁移，无须一次设计完所有表。
4. **逐接口替换模拟数据**：接口实现后在共享测试环境验证真实请求、权限、异常和状态迁移；一条流程联调通过后再标记完成。

前端代码只读取 `API_BASE_URL` 之类的环境配置，不能把某位同学的 IP 或 `localhost:8080` 写死在页面中。开发环境可以统一用前端开发服务器的 `/api` 代理；共享测试环境固定一个域名或地址并通过反向代理转发到后端。这样后端换机器或端口时，只改环境配置，不要求每位同学修改业务代码。正式环境的数据库端口不向普通用户开放。

成功响应返回资源及状态；创建成功使用 `201`。常见错误：`400 VALIDATION_ERROR`、`401 UNAUTHENTICATED`、`403 FORBIDDEN`、`404 NOT_FOUND`、`409 RESOURCE_CONFLICT / INVALID_STATE / SELF_APPROVAL_FORBIDDEN`。错误体统一为 `{code, message, details, requestId}`。会改变状态的接口支持 `Idempotency-Key` 或等效防重复机制，防止手机网络重试造成重复预约或重复交接。

登录建议采用服务端会话和安全 Cookie；统一入口通过 HTTPS 反向代理转发前端与 API。修改状态的请求加入 CSRF 防护。账号初始由管理员建立，不开放无审核的公共注册。上传照片仅允许指定图片类型和尺寸，经服务端校验后保存；图片访问须受权限控制，不把存储密钥暴露给浏览器。

### 5.1 身份与权限（负责人：1号；前端对接：2号）

| 方法与路径 | 用途 | 核心字段或约束 |
|---|---|---|
| `POST /auth/login` | 登录 | 账号、密码；返回当前用户资料与权限。 |
| `POST /auth/logout` | 退出 | 失效当前会话。 |
| `GET /auth/me` | 当前身份 | 返回角色及资源范围；前端据此展示入口。 |
| `GET /users`、`POST /users` | 查询/建立账号 | 仅有授权的管理员使用；支持启停。 |
| `PATCH /users/{userId}` | 修改账号状态 | 不物理删除有历史记录的用户。 |
| `GET /users/{userId}/grants`、`PUT /users/{userId}/grants` | 查看/调整角色及资源授权 | 修改者、原因、变更前后写入日志；禁止自己随意扩大自己的权限。 |
| `GET /reviewers`、`POST /reviewers`、`DELETE /reviewers/{userId}` | 维护审核小组 | 成员动态变更，已有审批记录不改变。 |

### 5.2 地点、物品、实物及照片（负责人：3号；前端对接：4号）

| 方法与路径 | 用途 | 核心字段或约束 |
|---|---|---|
| `GET /locations`、`POST /locations`、`PATCH /locations/{id}` | 列表、添加、修改办公室/物资室 | `name`, `type`, `status`；不写死数量。 |
| `GET /items`、`GET /items/{id}` | 浏览物品 | 按地点、关键字、可借状态筛选；返回图片和库存摘要。 |
| `POST /items`、`PATCH /items/{id}` | 上架/编辑物品 | `locationId`, `isValuable`, `status`, `rules`；贵重标记由管理员设置。 |
| `POST /items/{id}/images`、`DELETE /items/{id}/images/{imageId}` | 上传/移除展示照片 | 管理员操作；限制类型、大小和张数。 |
| `GET /items/{id}/units`、`POST /items/{id}/units` | 查看/增加具体实物 | 每件具有唯一 `unitCode`。 |
| `PATCH /items/{id}/units/{unitId}` | 维护实物 | 维修、停用、遗失等状态；不得覆盖未归还记录。 |
| `GET /items/{id}/availability?startAt=...&endAt=...` | 查询时段库存 | 仅供展示；最终可用性由提交预约接口再次判定。 |

### 5.3 会议室（后端：5号；前端：6号）

| 方法与路径 | 用途 | 核心字段或约束 |
|---|---|---|
| `GET /rooms`、`GET /rooms/{id}` | 会议室列表与详情 | 返回容量、开放时段、停用信息。 |
| `POST /rooms`、`PATCH /rooms/{id}` | 添加/调整会议室 | 管理员权限；两间仅为初始数据。 |
| `GET /rooms/{id}/calendar?from=...&to=...` | 查询占用日历 | 不暴露其他申请人的敏感信息。 |
| `POST /rooms/{id}/blackouts`、`DELETE /rooms/{id}/blackouts/{blackoutId}` | 管理停用时段 | 维修、活动占用等须说明原因。 |

### 5.4 预约、审批与交接（后端：3号、5号；前端：2号、4号、6号）

| 方法与路径 | 用途 | 核心字段或约束 |
|---|---|---|
| `POST /reservations` | 创建物品或会议室预约 | `{resourceType, resourceId, startAt, endAt, purpose}`；返回 `id`, `status`, `submissionSeq`。物品一次申请默认数量 1，批量借用另加 `quantity`。 |
| `GET /reservations/{id}`、`GET /me/reservations` | 查看详情/我的预约 | 返回审批、交接和当前状态。 |
| `GET /reservations` | 管理端筛选预约 | 按资源、状态、时间、申请人筛选；须按管理范围授权。 |
| `POST /reservations/{id}/cancel` | 用户或管理员取消 | 管理员代取消须写原因；已借出不能直接取消。 |
| `GET /approval-queue` | 审核工作台 | 返回当前审核人可处理且有顺位资格的申请。 |
| `POST /reservations/{id}/decision` | 单人审批 | `{decision: APPROVE\|REJECT, reason}`；禁止自审，审核通过时再次检查容量。 |
| `POST /reservations/{id}/pickup` | 用户确认取件 | `{unitIds}` 由交接时确认；只允许本人且预约已确认。 |
| `POST /reservations/{id}/return-submission` | 用户提交归还 | `multipart/form-data`：至少 1 张照片、可选 `remark`；进入待核验。 |
| `POST /reservations/{id}/return-verification` | 管理员核验 | `{decision: ACCEPT\|REJECT, reason}`；接受后实物可重新分配。 |
| `POST /reservations/{id}/override` | 辅导员处理已确认的会议室冲突 | `{action, reason, replacementSlot?}`；必须通知受影响用户并记日志。 |

建议将业务动作设计为命名明确的端点，而不是让前端直接 `PATCH status`；合法状态迁移由后端控制。对“取件确认是否需要管理员一起确认”的实际线下流程，首版按用户自行确认实现，同时保留管理员日志与异常处理能力。

### 5.5 日志、提醒与配置（负责人：1号、5号、6号）

| 方法与路径 | 用途 | 核心字段或约束 |
|---|---|---|
| `GET /audit-logs` | 管理端检索日志 | 按对象、操作者、时间和动作过滤；只读。 |
| `GET /me/notifications`、`POST /me/notifications/{id}/read` | 查看/标记提醒 | 审批结果、取件、逾期、优先占用等。 |
| `GET /settings/booking`、`PUT /settings/booking` | 查询/修改预约规则 | 提前天数、最长时长、审批超时等；变更写日志。 |
| `GET /health` | 部署健康检查 | 只公开必要健康信息。 |

`worker` 只通过受保护的内部接口领取/提交待处理任务，或由核心 API 提供专用任务端点；不得复用普通用户身份。跨机器调用必须鉴权、超时、可重试且避免重复执行。短信、邮件、微信通知不是首版硬依赖；先保证站内提醒，外部渠道以后接入。

## 6. 数据表与代码边界

建议最少包含 `users`, `role_grants`, `reviewer_memberships`, `locations`, `items`, `item_images`, `item_units`, `rooms`, `room_blackouts`, `reservations`, `approval_decisions`, `pickup_records`, `return_submissions`, `audit_logs`, `notifications`, `system_settings`。表名和字段以数据库迁移及 OpenAPI 为准，本文只规定必须承载的概念。

前端按页面/功能拆模块，统一使用一个 API 客户端；不得在页面中散写请求地址和状态字符串。后端按 `auth`, `catalog`, `booking`, `approval`, `handover`, `audit` 分包，业务规则放在服务层，控制器不直接拼 SQL。跨模块只能调用公开服务接口，不能直接改别人的表状态。图片文件放对象存储或受控文件存储，数据库只保存元数据与引用；不得把图片二进制直接塞进预约表。

## 7. 质量门槛与联调节奏

1. **第一周先冻结接口骨架**：三组共同确认状态图、数据库核心表和 OpenAPI；前端可以基于示例响应开发，后端按同一契约实现。
2. **每个 PR 自检**：构建通过；新增接口有权限和参数校验；状态迁移有测试；新增字段有迁移脚本；OpenAPI 与代码同步；页面在手机和电脑宽度可操作。
3. **关键自动化测试**：同一会议室同一时段双请求只能有一个有效确认；贵重物品未审不得取件；申请人不能自审；一名审核人同意即可通过；库存为 2 时最多 2 个有效占用；归还缺照片失败；未核验实物不可再借；辅导员优先处理与已确认预约的显式覆盖均有日志。
4. **每周集成**：周中合并小 PR 到 `develop`，周末由全组按真实流程验收并发布到 `main`。发现契约冲突当天在 Issue 中定方案，不让前后端各自兼容不同字段。
5. **上线准备**：测试环境和正式环境分开；HTTPS；密钥以环境变量管理；每日备份数据库和照片、定期实际恢复；记录服务器、域名、责任人、到期时间与故障处理步骤。正式部署至少完成一次两机联调和一次备份恢复演练。

## 8. 六人责任与交付物

| 人员 | 主责 | 每周必须提交的证据 |
|---|---|---|
| 1号（组长） | 权限、接口总约束、集成、部署协调 | 可运行集成版、接口变更记录、自己的代码与 PR |
| 2号 | 用户端、手机适配、登录与我的预约 | 页面代码、接口联调记录、手机浏览器演示 |
| 3号 | 地点/物品/实物/照片/取还件后端 | 数据迁移、接口、核心规则测试 |
| 4号 | 物品端与资源管理后台 | 上架、库存、取还件页面与联调结果 |
| 5号 | 预约并发、会议室、审批规则后端 | 冲突测试、优先级测试、接口与日志 |
| 6号 | 会议室日历、审核工作台、独立任务服务 | 页面、跨机器任务调用、逾期/超时演示 |

搭档为 `1+2`、`3+4`、`5+6`，每对交付一条页面到数据库的完整流程。代码评审尽量跨搭档进行，避免只有搭档之间知道实现。个人贡献用 Issue、提交、PR、测试和演示记录评价，不以代码行数单独评判。

### 8.1 开发先后与依赖：先契约，后并行，逐条联调

**不要让六个人按编号排队开工。** 真正共同依赖的是第一周的业务状态、数据字段、API 契约和可启动的项目骨架；各模块的页面与后端随后并行开发。5号不是专职测试员，6号也不只是画页面；测试由功能负责人编写，全组参与验收。

| 阶段 | 先完成什么 | 谁可以同步开始 | 阶段验收 |
|---|---|---|---|
| A：第 1–2 天 | 1号组织六人确定状态图、权限、接口字段；搭空工程、数据库迁移和健康检查 | 2/4/6号画页面流程；3/5号设计本模块表和接口 | 所有人按 README 能运行骨架；OpenAPI 有首批接口与示例 |
| B：第 3–5 天 | 1号实现账号/权限最小闭环；3号实现地点、物品、照片、实物编号基础；5号实现预约与冲突检查基础 | 2号做登录/用户端；4号做上架/物品端；6号做会议室日历/审核台；前端先用约定的模拟响应 | 真实账号可访问一个真实物品接口；前端页面能独立演示 |
| C：第 2–4 周 | 3号物品/取还件接口与4号页面联调；5号预约/审核接口与2、6号页面联调 | 1号持续合并、补权限与公共错误处理；6号启动独立任务服务 | 从页面完成“上架→预约→审核→取件→拍照归还→核验” |
| D：其后 | 全组集中验证并发、权限、状态异常和跨机器部署 | 各人修自己模块的问题并互相审查 | 两机演示、测试记录、备份恢复和操作手册 |

最小依赖关系为：`账号/权限契约 → 需要登录的真实接口联调`；`物品和会议室基础数据 → 真实预约创建`；`预约状态与审批规则 → 取件、归还和审核页面联调`。**页面开发不依赖真实接口全部完成**：前端先按 OpenAPI 的示例响应开发，后端实现后再逐个替换。与此相反，真实预约接口必须依赖可靠的资源数据和冲突规则，不能用临时页面逻辑代替。

每周安排 2 次固定联调，每次只验收一条完整流程；接口不一致由该模块的前后端负责人当天共同修订契约，不交给组长单独“补胶水”。建议首次联调顺序为：`登录＋物品浏览` → `物品上架＋照片` → `普通物品预约` → `贵重物品审批` → `取件＋归还` → `会议室审批＋辅导员优先`。

## 9. 仓库创建当天的清单

1. 创建一个 GitHub 仓库，添加六位成员和 `README.md`、本文、`LICENSE`（如确定开源）及 `.gitignore`。
2. 建 `main`、`develop`，配置保护规则与至少一人审查、构建通过后合并；先提交空工程和自动构建。
3. 在 GitHub Issues 建立六个模块任务及首周业务规则任务；把三张状态图和第一版 `contracts/openapi/openapi.yaml` 纳入首周交付。
4. 建立共享测试环境与测试账号；使用虚构测试数据，不上传学院真实账号密码和学生隐私数据。
5. 向课程教师确认：核心 API 与独立任务服务部署在不同机器是否满足课程对“多个分布式子系统”的认定；如果需更明确的子系统交互，调整部署图和演示方案。
